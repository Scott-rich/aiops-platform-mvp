# 第六阶段：性能与效果评估

本阶段新增独立评估工具，复用现有 HTTP 服务、事件协议、Pipeline、检测器和 RCA。无需迁移数据库，不修改现有 API、规则和模型诊断流程。每次创建新目录和新数据库，不读取或清理用户已有数据库。

## 干净环境与复现

使用 Linux/WSL、Python 3.11/3.12、Java 17。仅 HTTP/算法回放不需要 Java；Linux `/proc` 不存在时资源数据为 null，对应资源检查失败，不能宣称资源测试完成。依赖继续使用现有锁定版本，无新增依赖。

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python -m unittest discover -s tests -v
# 真实SIGTERM清理、非法参数、输出目录保护：
python -m scripts.verify_benchmark_controls --output artifacts/benchmark-control-check

# 首次联网下载 Apache Kafka 3.9.1 并校验官方 SHA-512；不自动安装系统 Java。
python -m scripts.bootstrap_fault_kafka --runtime-dir /tmp/aiops-phase6-kafka

# 本轮主测：每档4秒、重复2次。输出目录必须不存在。
python -m scripts.benchmark_platform \
  --output artifacts/benchmark-01 \
  --kafka-home /tmp/aiops-phase6-kafka/kafka_2.13-3.9.1

# 再运行同参数（仅改变输出路径）即可比较。
python -m scripts.benchmark_platform \
  --output artifacts/benchmark-02 \
  --kafka-home /tmp/aiops-phase6-kafka/kafka_2.13-3.9.1
python -m scripts.compare_benchmarks \
  artifacts/benchmark-01/result.json artifacts/benchmark-02/result.json \
  --output artifacts/comparison-01.json
```

退出码：0=所选组件通过；1=运行/一致性/清理失败；2=存在 blocked 或未启用的组件；130=中断。默认 all 在未配置真实模型时返回2，HTTP/Kafka/evaluation 的 passed 仍有效，整体不能写成全部通过。比较命令返回2表示配置、环境、源码或协议不同，避免无条件生成“提升百分比”。描述性比较不等于统计显著性检验。

每次只接受固定本机回环地址；新建专属 API、四服务、Kafka broker、topic/group 和数据库，不接受外部业务目标。不需要宿主机网络管理权限，不执行资源耗尽。子进程清理、限时请求、20秒 Kafka 排空上限均内置；Ctrl+C/SIGTERM 会清理，SIGKILL/断电仍需人工检查遗留进程。

## 分组件和积压实验

```bash
# 不需要 Kafka 或模型：真实5个HTTP进程，业务和事件入口分别压测。
python -m scripts.benchmark_platform --component http --output artifacts/http-bench \
  --business-rates 2,5,10 --ingest-rates 20,60,120 --duration 4 --repeats 2 --concurrency 16

# Kafka生成→broker→现有Python持久化/快速检测路径。并非Flink引擎。
python -m scripts.benchmark_platform --component kafka --output artifacts/kafka-slow \
  --kafka-home /tmp/aiops-phase6-kafka/kafka_2.13-3.9.1 \
  --kafka-rates 50,150,300 --duration 3 --repeats 1 --consumer-delay-ms 350

# 固定/动态共用同一700窗口标签数据，另评估12个RCA算例。
python -m scripts.benchmark_platform --component evaluation --output artifacts/quality-bench
```

参数上限：每类1–5个不同速率，每档1–1000/s，时长1–60秒，重复1–5次，并发1–64；整次计划输入不超过20000条、业务请求不超过3000条。Kafka 每批最多50条，单批消费延迟0–2000ms。目标速率超过本机能力时保留失败/跳过/排空超时，不能以目标速率代替实际吞吐。默认小规模测试用于可复现研究，不声称容量极限。需要容量结论时，应在固定专属硬件上延长测试并明确SLO与稳态区间。

## 指标定义与真实性

| 指标 | 真实测量与边界 |
| --- | --- |
| 业务吞吐 | 成功 gateway 请求 / 发送加排空耗时；每个正常请求产生12条真实遥测。记录失败和未能启动的请求。 |
| 事件入口吞吐 | 成功 `/demo/ingest` 请求 / 发送加排空耗时，每个请求一条schema v1事件。 |
| Kafka事件吞吐 | 持久化完成的唯一测试事件 / 发送加排空耗时；同时记录 producer 确认数、失败数。 |
| HTTP延迟 | monotonic 时钟的发送到完整响应；提供全部尝试与成功请求的p50/p95/p99。业务响应包含同步遥测开销；入口204表示持久化返回。 |
| Kafka端到端延迟 | 同一进程 monotonic 时钟：事件创建到独立消费线程执行生产 `persist_batch` 返回，包含存储和快速检测；此时尚未commit Kafka offset。 |
| 接收时间差 | `ingested_at - event_time` 另列。存储时间戳在事务开始前生成，因此绝不叫“提交完成延迟”。墙钟可能跳变，负差标记缺失。 |
| 检测延迟 | 实际HTTP支付/库存5xx注入：控制确认→第一条匹配告警、根因服务首错事件→告警；只统计 fast_errors 通道。Kafka首错→快速告警另列。 |
| 窗口检测延迟 | 合成回放中事件时间上的异常区间→命中窗口延迟，与真实处理耗时分开；漏检保持null。 |
| CPU | `/proc/PID/stat` 的utime+stime差 / monotonic采样间隔，单位单核%；总和可超过100，首样本为null。PID复用/失踪不产生伪0；PID命名空间不一致时按PPid/NSpid核对本进程拥有的子进程，避免误读无关PID。 |
| 内存 | 同批次本次拥有PID的RSS之和，可能重复计算共享页。HTTP包含API+四服务；Kafka包含broker+驱动/消费者进程。非整个宿主机占用。 |
| Kafka积压 | broker end offset - consumer group committed offset，约每200ms采样；观测非原子快照，峰值是采样峰值，可能遗漏瞬时尖峰。采样开销包含在本机实测中。 |
| 准确率/精确率/召回率 | 明确合成700窗口标签与真实故障样例的来源；abstention在全标签混淆矩阵中视为无告警，同时单列覆盖率。 |
| RCA Top-1/Top-3 | 候选前k命中任一独立根因标签；执行失败仍进分母；多根因覆盖率另列。真实两故障与12个合成算例分别出数。 |
| 模型耗时/费用 | 持久审计中真实attempt的耗时、usage及配置单价估算；复用报告不重复计费；失败重试计入，未知usage/单价时总费用null。 |

运行时依赖图：独立负载器分别访问 gateway→order→payment/inventory 和 HTTP事件入口；五个HTTP进程共同写本轮隔离存储。Kafka实验由独立broker及消费者线程组成，消费者调用原有持久化和快速检测。Flink窗口性能需要另外启动既有native工具，本阶段没有将Python路径标记为Flink实测。

## 模型费用入口

仅显式 `--real-model` 才允许产生真实模型请求；缺配置时 blocked，不构造模型答复。普通吞吐实验移除LLM环境配置，避免负载触发收费。

```bash
# LLM_BASE_URL、LLM_MODEL、LLM_API_KEY通过终端安全注入；不将真实密钥写入仓库。
# 可选单价（单位每百万token）和币种使用既有变量：
# LLM_INPUT_PRICE_PER_MILLION、LLM_OUTPUT_PRICE_PER_MILLION、LLM_COST_CURRENCY。
python -m scripts.benchmark_platform --component model --real-model \
  --output artifacts/model-bench
```

复用 `scripts.verify_llm`：默认使用保留的、哈希有效的历史真实故障证据；可传 `--model-evidence /path/to/report.json`。单次命令最多1次模型HTTP尝试、20秒请求超时、30秒总预算；模型验证子进程50秒上限。原有结构/证据校验不放宽。费用是usage×用户配置单价的估算，不是账单；缺usage时不能假定免费，也不估算未发生的调用。测试用的伪造attempt只在单元测试中使用，不进入实际结果。

## 文件与追溯

- 根 `result.json`：状态、实际开始/结束、配置、Python/依赖/CPU/cgroup环境、源码哈希及所有组件结果。
- `completed.json`：终态和根JSON的SHA-256；运行尚未结束时不应有终态文件。
- `metrics.csv`、`report.md`：每档/重复的测量结果，空值表示未测得。
- `http/requests.jsonl`、`resources.jsonl`：每个实际请求和进程资源采样；`http/result.json`保存真实trace RCA和告警证据。
- `kafka/events.jsonl`、`lag-resources.jsonl`：发送、处理完成、offset及lag时间序列；`broker/`保留日志和配置；测试库仅属于本轮。
- `evaluation/detection/`：输入JSONL、决策CSV、指标CSV与JSON；`evaluation/rca/`：算例CSV、证据核验和Top-k结果。
- `model/result.json`：真实调用状态、耗时、usage和费用统计；缺配置时不含伪造attempt。

压缩包排除本阶段可重建的Kafka segment与Python缓存，保留原始JSONL、日志、测试数据库、历史阶段材料。没有新增凭证文件、数据库迁移或业务配置覆盖。官方定义参考：Linux `/proc` 文档 https://www.kernel.org/doc/html/v6.14/filesystems/proc.html 、kafka-python消费者文档 https://kafka-python.readthedocs.io/en/2.1.3/apidoc/KafkaConsumer.html 。
