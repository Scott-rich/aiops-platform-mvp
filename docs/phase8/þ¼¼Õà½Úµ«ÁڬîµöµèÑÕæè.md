# 第八阶段验收报告

本次在第七阶段完整项目上增量完成证据管理与报告系统升级。**第八阶段核心验收通过**：超过原扫描/分析上限的证据可完整冻结、分页读取和校验；报告保留原接口并明确标注分析截断；版本比较、归档恢复、受保护的原始事件清理均有真实执行记录。

本轮没有进行真实外部大模型调用、Docker 部署或高可用验收，不把这些能力算作通过。修改前源码备份见 `source-before-phase8.zip`；修改前哈希见 `baseline.json`；逐文件差异见 `changed-files.json`。最终源码哈希和机器可读汇总位于 `artifacts/phase8/`。

## 真实证据闭环

- 输入为 **23,005 条关联事件 + 20,100 条无关事件**；明确属于带标签的合成遥测。Uvicorn、SQLite、HTTP 请求、归档及事务操作为真实执行。
- 关联证据保存 23,005 条，分析快照仍为 1,800 条，报告状态 `analysis_sampled`。客户端通过 **116 页**读完，逐记录校验，无重复/遗漏；重算整集 SHA-256 与报告一致。
- 组合服务、类型、事件 ID、trace 和闭区间时间筛选命中准确；非法游标返回 422。故障入口返回固定报告 ID，后续分页绑定该版本。
- 在已有 enriched 报告后加入一条晚到事件，产生 v3；旧报告 JSON 不变；比较接口准确返回 1 条新增，历史 API 分页返回 v1/v2/v3。
- 导出完整集后，恢复 23,005 条事件至新数据库，事件原文、来源和接收时间共同生成的完整集 ID 与原集一致。
- 清理默认预览；显式执行真实删除 200 条原始事件前，已生成 SQLite 备份和经校验的归档。报告及冻结证据完整校验仍通过；再从归档恢复 200 条。
- 实际终止并重启查询 API 后，历史报告逐字段一致，完整证据哈希仍通过。
- 用第七阶段真实运行库副本验证迁移，原有 **225 条事件、3 个报告版本**及其他原表内容哈希保持一致；只向迁移表追加 phase8 记录。源文件 SHA-256 不变，升级副本 integrity_check 为 ok，自动备份存在。
- 真正运行 Kafka 3.9.1 / Flink 1.20.3 / connector 3.3.0-1.20 / Java17，验证乱序、迟到、重复/冲突、毒消息、Python/Flink 对比、checkpoint 和 TaskManager 恢复，以及真实 HTTP 级联故障。此处与合成证据分页实验是不同运行。

## 未解决问题与下一阶段

1. **外部真实模型与 Docker 仍未验证。** 本阶段不需要模型密钥或 GPU；原生链路需要 Linux、Java17 和本轮已安装的 Python3.11/Kafka/Flink。模型服务只沿用环境变量配置，没有提交真实密钥。
2. 完整集仅覆盖冻结时已入库的匹配数据，跨主题数据到齐仍未知；模型上下文、规则/RCA分析快照继续有预算。已 resolved 的故障沿用原生命周期，不自动重开诊断迟到数据。
3. 完整证据版本可能重复占用磁盘。当前保留原始事件最少 30 天（可配且最少 7 天），清理必须显式执行；**冻结集、报告和备份不自动淘汰**。跨版本去重、离线归档查询和长期自动清理未实现。
4. 同一 SQLite 写锁下的大证据集采集会增加报告延迟，其他请求可能短暂 503；操作有截止时间，超大集可能需要调节到最多 120 秒。没有宣称高吞吐无回归或多副本高可用。
5. 归档每行 2 MB、恢复/冻结有截止时间；超限会失败并保留原始库，不宣称无限容量。磁盘断电持久性、远程访问安全、全 JobManager 故障切换未在本轮验证。
6. PyFlink 单元进程退出仍有两条 Java gateway 管道 ResourceWarning；测试通过不等于该历史警告已修复。历史 SQLite 损坏根因仍未知，本轮只验证新库与旧库副本完整性。
7. 控制台通过语法和服务端接口检查，未跑浏览器点击 E2E。

下一阶段按原计划进行第九阶段工程化收口：统一配置校验和结构化日志、明确初始化/迁移与生命周期、依赖和密钥检查、自动化 CI、干净环境部署验证。若平台需要远程暴露，应先落实身份认证和高风险操作权限控制；继续保持核心链路可运行，不以文档代替实测。
