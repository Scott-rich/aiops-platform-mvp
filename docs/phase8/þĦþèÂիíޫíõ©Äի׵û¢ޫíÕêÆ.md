# 第八阶段：现状审计与实施计划

本次基线为已交付的第七阶段完整项目，继续迭代证据与报告模块，不替换检测器、消息协议或模型接口。修改前源码及配置已备份至 `source-before-phase8.zip`，逐文件哈希见 `baseline.json`。历史数据库只在副本上执行升级测试。

## 实施顺序及验收

1. 新增 `app/evidence.py`：数据库增量建表前在线备份；按一致事务流式冻结完整证据，保留有界分析快照；游标分页、组合筛选、流式哈希。验收：超过 20,000 条仍完整读取、重放无重复、晚到数据不改变旧集、篡改/缺行可检出。
2. 修改 `storage.py`、`reporting.py`、`diagnosis.py`、`api.py`，新增证据 API：保留旧字段含义，明确原始集完整性、分析截断和引用；新版本历史分页及比较。验收：旧报告仍可读取，旧报告完整性标记未知；新证据产生新版本；非法游标/筛选返回可理解错误。
3. 新增归档与保留 CLI：默认预览；显式执行时先备份和校验归档，再有限批次清理原始事件；保护活动故障及未生成报告的告警，保留冻结证据与历史报告。验收：归档恢复、失败不删除、活动事件保护，测试只操作临时隔离库。
4. 补充单元测试及独立真实 HTTP/SQLite 集成脚本，运行完整回归及既有原生 Kafka/Flink 测试；保存 JSON、日志及失败记录。更新配置示例、README、部署与验收文档，交付完整 ZIP。

## 风险与兼容性

- 全量证据增加磁盘使用；按批读取限制内存，截止时间限制单次冻结/校验工作。首次全量采集可能增加报告生成耗时，不能宣称性能无影响。
- 本阶段完整性仅指查询事务时已经入库、符合关联规则的事件；跨 Kafka 主题没有共同 watermark，不能证明所有遥测已到达。
- 模型上下文仍有预算；保存全部证据不等于模型分析全部证据。旧 `audit.evidence_set_id` 保持模型上下文含义，另增完整集字段。
- 全量哈希是本地一致性检查，不是外部签名。默认不删除冻结证据、报告或备份；保留策略不能被解释为无限磁盘容量。
- SQLite 单节点及当前锁策略不变；不声称高可用。删除操作不通过远程 API 暴露。
