# 第二阶段复核与实施范围

## 修改前复核

基线为第一阶段交付版本3，SHA-256及修改前整包备份见 `backup.json`。复核范围包括 `app/diagnosis.py`、`reporting.py`、`retrieval.py`、`storage.py`、本地启动器、worker生命周期、Compose、`.env.example`及既有核心/报告/API测试。既有事件、API、快照和历史报告格式继续使用。

| 状态 | 修改前证据与缺口 |
| --- | --- |
| 已实现 | 规则诊断、初报/补证/恢复版本、实际观测与SHA-256、服务/规则/关键词案例检索 |
| 部分实现 | 兼容HTTP模型封装、支持证据ID校验、一次模型尝试标记；缺少完整Schema、稳健时限、持久化HTTP预算和统一审计 |
| 仅有配置未验证 | 模型地址/名称/密钥环境变量；第一阶段真实模型调用0次 |
| 尚未实现 | 有限重试与全局限流、未知结论结构、置信依据、严格候选服务/本服务引用校验、真实模型独立集成验收 |

## 本阶段计划与风险

1. 备份第一阶段；增量加入Schema与上下文，不更改原始事件数据。验收：旧报告读取、快照哈希和既有API回归通过。
2. 抽取HTTP适配器与环境配置，限定总时间、重试、字节数及预算。风险：不同供应商的response_format能力不同，默认none。验收：HTTP测试替身覆盖真实传输层错误路径，明确不称为模型实测。
3. 增加SQLite调用任务与尝试审计，先在线备份再建表。风险：进程在供应商完成后崩溃导致费用和答案状态不明。验收：并发预占、重启、遗留记录、未知调用保守处理及结果复用测试。
4. 用实际历史HTTP/Kafka证据调用真实模型。风险：无API密钥、网络/CPU限制或小模型能力不足。验收：脚本独立记录blocked/failed/passed，规则回退不得计模型通过。
5. 执行完整单元回归及实际Kafka/Flink和本地HTTP回归；更新部署说明和本阶段验收报告。没有Docker仍单列容器未验收，不把原生运行说成容器部署完成。
