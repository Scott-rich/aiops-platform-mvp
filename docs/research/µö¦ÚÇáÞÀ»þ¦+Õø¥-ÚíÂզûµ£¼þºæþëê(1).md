## 0. 一句话诊断

工程完成度在本科里属前 5%（464 测试、85% 语句覆盖、哈希可核、验收脚本可跑通真实 Kafka→Flink→SQLite→LLM）；
**但"科学有效性"在本科里只是中位水平**——所有指标都建立在自己造的合成数据上，没有外部基线、没有统计检验。
面试官/评委不会因为"你能跑"给高分，只会因为"你证明了什么别人没证明的"给高分。

## 1. 七个硬伤（按被问死的概率排序）

### 1.1 数据不可信：自造数据自证（最致命）

现状实测：

- 服务拓扑 4 个（gateway / order / inventory / payment），全部同机；
- 合成数据生成器（`simulator/`、`cases/*.json` 仅 3 个案例）；
- 峰值 120 events/s、突发 3 秒、`repeats=1`；
- 全仓**零**引用：SMD、SMAP、MSL、SWaT、PSM、GAIA、TrainTicket、Online Boutique、AIOps Challenge、KDD Cup AIOps。

后果：`动态 0.9919 准确率 / 14-of-18 episode / RCA Top-1 8/8` 只对"你自己的生成器"成立。评委一句话就能拆：
"换个数据集还成立吗？"——现在的答案是不能答。

修法（二选一，别贪多）：

- **A 路线（低成本）**：接公共时序异常数据集做检测对照（SMD / SWaT / PSM），把"检测器"单独抽成模块，输出统一 PR/ROC。
- **B 路线（高价值）**：TrainTicket 或 Online Boutique 上用 Chaos Mesh 做真实故障注入（延迟/丢包/CPU/依赖不可用），
  标签来自注入编排而不是人工标注，天然可信。至少 8 个服务、3 层调用链、跑 30 分钟以上的连续负载。

验收标准：在**非自造**数据上复现出"动态优于固定阈值"的结论，且给出置信区间。

### 1.2 没有基线、没有消融（"自比自"）

现状：检测只比"固定阈值 vs 自己的 median/MAD"；RCA 只有规则打分；模型只跑一个 Qwen1.5B。
缺的对照：SPOT / StreamSpot / IForest / LSTM-AE / OmniAnomaly / TranAD / Anomaly Transformer；RCA 缺 MicroRCA / CIRCA / Eadro / Nezha / GNN-RCA。
缺的消融：25ms 直方图、相对裕度 0.2、6h 时间分桶、truncation 保守策略——各自贡献多少？

修法：至少 3 个外部基线 + 4 组消融，表格直接进论文/答辩 PPT。

### 1.3 统计不成立

现状：`repeats=1`；RCA 有标签样本 **n=8**；单次 3 秒突发；报告只有单次 p95。
`8/8` 的 95% 置信区间约 `[63%, 100%]`——统计上等于没结论。

修法：

- 每个配置 ≥5 次重复（不同 seed），报告 mean ± std；
- RCA 扩到 ≥50 个注入案例，样本量足够再说准确率；
- 用 bootstrap CI + McNemar / Wilcoxon 做显著性；
- 画 risk–coverage 曲线（对"弃权"策略尤其重要）。

### 1.4 "检测"其实是 4 个阈值

`flink/rules.py` 实体：`p95 > 800ms`、`error_rate > 0.2`、`cpu > 90`、`memory > 90`。
`flink/adaptive.py` 是 median/MAD 3σ + 相对裕度（1970s 方法，工程上合理，科研上不新）。
**日志完全没进检测**（`event_type=log` 只用于上下文/RCA）；**没有 trace 级异常检测**。

必被问："这和 Nagios/Zabbix 有什么区别？" 现在只能答"我有 LLM 和报告"，答不住"检测本身"。

修法：加一个日志模板/序列异常基线（Drain + 频次突变即可），或把 trace 的 span 时长分布纳入检测，形成"指标+日志+链路"三模态。

### 1.5 LLM 是最大亮点，但一点都没被量化（最可惜）

现状：`grounding / abstention / 原始输出审计 / 置信上限 low` 的设计是**全项目最像研究的部分**；
但完全没有度量：证据选择 P/R、幻觉率、abstention 校准（risk–coverage、ECE）、提示注入鲁棒性（日志里塞"忽略以上指令"）、模型规模/成本/延迟曲线、人类评估一致性。

修法（强烈建议做成毕设主线）：
在现有协议上补 4 个实验：①证据选择 P/R/F1；②risk–coverage 曲线（覆盖率 vs 错误率）；③提示注入攻击成功率（3 类攻击 × 20 payload）；④0.5B/1.5B/7B（或 API）成本-延迟-准确率权衡。
这四张图足以支撑一篇 workshop paper 或省级优秀毕设。

### 1.6 "分布式"名不副实

现状：单机；Flink 1 个 TM / 2 slot；SQLite 单文件；4 个假服务同宿主；无 k8s/Helm、无多节点、无网络分区、无时钟漂移测试。
报告里"distributed"用词会被抓。

修法：要么补齐 k8s（StatefulSet + PVC + 多节点 kind/minikube 至少 3 节点）并做一次"杀 Pod / 断网 / 磁盘满"实验；
要么老实改口径为"单机原生栈（Kafka+Flink）"，把多节点列为 future work。**改口径比硬吹安全**。

### 1.7 工程规范的显性缺口（面试官 5 分钟就能看出来）

| 项 | 实测 | 顶尖要求 |
|---|---|---|
| Lint | `ruff` 生产代码 **73** 条（blind-except 61 全仓、unused-import 41、B023 1、subprocess 无 check 11） | CI 阻断，0 error |
| 类型 | `mypy --disallow-untyped-defs` **547** 处，等于没做类型检查 | 核心模块 `disallow_untyped_defs` + CI |
| 配置 | 无 `pyproject.toml` / `setup.cfg` / `.pre-commit-config.yaml` | 三件套齐全 |
| 覆盖率 | **85%**（app+flink，语句）——这个不错 | 有门禁（如 ≥80% 阻断） |
| 自监控 | 无 `/metrics`，无 Prometheus，无自带 trace | 平台自己可观测 |
| API | 22 个 endpoint，无版本前缀、无限流、无统一错误码表 | `/v1`、限流、错误码 |
| 部署 | Dockerfile 单阶段、无 healthcheck、无 k8s/Helm/IaC | 多阶段 + Helm + 健康检查 |
| 供应链 | 有 SHA 校验（好），但无 SBOM、无镜像扫描 | trivy/syft 进 CI |
| 仓库 | **无 .git 历史、无 LICENSE、无 CHANGELOG**、2.2G（2.1G 是 artifacts） | 有提交历史、LICENSE、Release、artifacts 外置 |
| CI | 仅 ubuntu + 3.11 单测一条 | 3.11/3.12 矩阵 + e2e + 性能回归门禁 |
| 可复现 | 需外网拉 Kafka（archive.apache.org 慢）与 HF 模型（国内不通），本次需换镜像才跑通 | 预构建镜像 / 本地离线包 / `make demo` 一条命令 |

## 2. AIOps 能力完整度对照

| 能力 | 现状 | 顶尖要求 |
|---|---|---|
| 指标异常检测 | ✅ 阈值 + median/MAD | 多算法对比 + 公共数据 |
| 日志异常检测 | ❌ 无（日志只作上下文） | Drain/模板 + 序列模型 |
| 链路异常检测 | ❌ 无（只做 span 传播） | trace 级异常 + 关键路径 |
| 告警关联/降噪 | ✅ 有（含预算与截断） | 要指标：降噪率、MTTA |
| 根因定位 | △ 规则 + 候选 + 证据 | GNN/因果 + 公共集 |
| 恢复确认 | ✅ 有（新鲜健康证据 + 否决） | 保持 |
| 变更/发布关联 | ❌ 无 | 变更事件进关联图 |
| SLO / 错误预算 | ❌ 无 | 至少演示一个 SLO |
| 容量预测 | ❌ 无 | 可选 |
| 处置闭环 | ❌ 明确不做（设计如此） | 受控建议 + 人工确认 |
| 数据漂移自适应 | △ 有 drift 场景，但无在线更新 | 概念漂移实验 |
| 多租户/权限 | ❌ local/token 两种模式，无 RBAC | 非必需 |

## 3. 90 天改造路线（三档，按投入产出排序）

> 对应提示词包中的阶段：档 1 = P0；档 2 = P1 + P3；档 3 = P2 + P4。
> 顺序不要改：**先有可信评测（P0），再谈真实系统（P3）**，否则真实数据跑出来的数也会被同样的质疑击穿。

### 档 1：把"证明"补上（3 周，必做 → P0）

1. 抽 `detectors/` 包：固定阈值 / MAD / IForest / SPOT(+可选 TranAD)，统一接口 + 统一评估脚本。
2. 接 **SMD + SWaT**（或 PSM）跑检测对照，输出 PR/ROC/F1 与逐数据集表格。
3. 统计升级：5 seeds、mean±std、bootstrap CI、显著性检验。
4. RCA 案例扩到 ≥40（脚本化注入 + 自动标签）。

交付：一张"跨数据集 × 多算法 × 置信区间"的主表。**这一张表就能把项目从"工程演示"拉进"研究"**。

### 档 2：把"真实"补上（4 周，冲奖/论文 → P1 + P3）

5. TrainTicket（或 Online Boutique）部署到 k8s（kind 3 节点），Chaos Mesh 注入 6 类故障。
6. 端到端跑 MTTD / MTTR / 告警数 / 事件数 / 报告采纳率，与"无平台"基线对比。
7. LLM 四联实验：证据 P/R、risk–coverage、提示注入成功率、模型规模权衡。
8. 加日志异常基线（Drain）与 trace 异常基线，凑成三模态。

交付：一套可重复的 `make e2e`，一条 5 分钟录屏，一张"注入→检测→关联→诊断→恢复"的时序图。

### 档 3：把"作品"补上（1 周，求职必备 → P2 + P4）

9. 仓库整理：拆 `platform/` 与 `research/`；artifacts 外置（release 附件或对象存储）；补 LICENSE、CHANGELOG、`.git` 历史（哪怕重建 30 个有意义的提交）。
10. `pyproject.toml` + ruff/mypy/pre-commit + CI 矩阵（3.11/3.12，lint/type/test/coverage/e2e 全绿徽章）。
11. `/metrics` + 限流 + API `/v1`；Dockerfile 多阶段 + healthcheck；Helm chart。
12. README 首屏：一句话问题、架构图、主结果表、3 分钟 demo、复现命令；英文版。
13. 写一篇 4000 字技术博客 + 一份 10 页毕设式技术报告（问题→相关工作→方法→实验→威胁→结论）。

## 4. 答辩 / 复试 / 面试 10 问预演（现在就要能答）

1. 你的检测和 Zabbix 有什么区别？→ 三模态 + 关联 + 证据约束诊断，阈值只是兜底。
2. 数据是你自己造的吗？→ 现在必须诚实回答"合成 + 我是为了验证管线"，并立刻给出档 1 的公共数据结果。
3. 0.9919 的准确率可信吗？→ 只能说"在我这个生成器上"，说清分布与局限。
4. 为什么不端到端 exactly-once？→ Flink checkpoint + Kafka 至少一次 + 业务幂等，代价与取舍。
5. LLM 会不会瞎编？→ 证据白名单 + 引用校验 + 弃权 + low 置信上限，附 risk–coverage 曲线。
6. 单机也叫分布式？→ 改口径或给 k8s 多节点实验。
7. 为什么用 SQLite？→ 单机研究定位 + 迁移到 PG 的抽象层（若补了，这里很加分）。
8. 这套系统上线要改什么？→ 存储、鉴权、租户、限流、TLS、可观测性、容量。
9. 你个人做了什么？→ 必须能指出 3 个"只有你能讲清"的设计决策与 1 个被推翻的方案。
10. 如果重做一次？→ 先定评测基准，再写代码（这句话本身就是成熟度信号）。
