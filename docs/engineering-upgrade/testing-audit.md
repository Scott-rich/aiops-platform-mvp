## 4. 性能与效果量化覆盖

| 指标 | 当前能力 | 验收缺口 |
| --- | --- | --- |
| 事件吞吐 | 演练保存累计事件；loadgen 输出累计 HTTP 状态与 in-flight | 没有固定区间提交/接收/处理事件速率、阶段耗时及输入速率矩阵 |
| 端到端处理延迟 | 部分事件和报告时间可查询 | 缺少 producer→Kafka→Flink→存储/告警的对应时间戳和 P50/P95/P99 |
| 检测延迟 | 历史单场景按轮询观察到首次事件的时间 | 缺少重复试验、时钟口径、故障真值匹配、分位数和未检出样本 |
| CPU/内存 | 只读 `/proc` 的可见节点均值；旧演练每 5s 采样 | 非平台进程/容器 RSS、CPU 或峰值；不是资源预算测量 |
| Kafka lag | 尚无 benchmark 指标采样 | broker/消费组 offset 与 lag 时间序列、追赶完成条件 |
| 告警准确率/精确率/召回率 | 固定规则 fixture 断言 | 无统一 TP/FP/TN/FN、真值时间窗、样本分母、漏检延迟 |
| RCA Top-1/Top-3 | 特定 fixture 断言首选 payment | 无独立标注场景数据集、多候选排名统计或不确定覆盖率 |
| LLM 耗时/成本 | 一次尝试预算有模拟测试 | 无真实模型测试结果、token usage/可配置单价/实测成本和失败耗时统计 |

`simulator/loadgen.py` 目标速率限制 0<RPS≤100，并发 1–200，达到上限会统计跳过，HTTP 超时 12s，停止会等待在途任务。这是有边界的流量发生器，尚非完整基准工具；固定等待间隔含循环开销，目标 RPS 不能直接作为实测吞吐。没有耗时直方图或 JSON/CSV 最终结果；随机基础延迟及概率故障未设独立种子。

观测开销需单列：服务在遥测发布前计算自身 request latency，但业务响应在发布完成后返回；上游又会包含下游发布等待，因此不同层的 latency 口径并不相同。HTTP 遥测每条同步超时 3s，单请求依次发送指标/span/log；发布在工作线程中等待，不阻塞事件循环但会延长响应。Kafka send 也可能等待 metadata。基准应同时记录客户端响应延迟、业务处理延迟、遥测发送耗时，避免将采集开销误归因到业务。

## 5. 恢复与可靠性

已实现并通过逻辑测试：事件/告警去重、事务批量校验、持久化事件与不可变报告、恢复需要新鲜连续健康样本、重复通知唯一键、旧告警不误重开、复发建立新事件。

尚未完成真实故障验证：Kafka 临时不可用与恢复、Flink checkpoint/作业重启、消费者落后追赶、数据库忙/只读/短暂不可用、平台进程重启后历史读取、端到端 LLM timeout/429/无效 JSON、真实网络超时恢复。不能据此宣称高可用。

具体风险：

1. Kafka worker 在启动阶段 `while True` 每 5s 重试，没有最大启动期限；运行阶段 poll/commit/数据库错误没有局部有界恢复，依赖进程退出及 Compose restart。证据先落库再提交 offset，意图为至少一次；提交失败后的实际重放必须联调。
2. HTTP 遥测失败记录计数后丢弃，没有重试、磁盘 spool 或补发；Kafka 异步发送耗尽重试/进程被杀也可能丢失。没有无限缓存是优点，但数据可能丢失的范围必须写清。
3. 本地 launcher 发现任一子进程退出后整体退出，无自动重启；shutdown 终止后超时 kill。持久化数据库保留，但尚无进程级重启读取验证。
4. 服务 `/health` 是存活状态，并未证明 Kafka/HTTP 遥测、下游或数据库可用。下游故障时服务依然可能返回 health=ok。
5. `/proc` 的 scope 明确为 proc-visible-node；在容器内不能自动等同于容器资源占用或宿主机完整指标。

## 6. 验证脚本与工程问题（需要优先修复）

- `scripts/verify_optimized.py` 使用 Python `assert` 执行核心验收，`python -O` 会跳过断言。其中 `all_hashes_and_references_valid`、`telemetry_failures_zero` 字段随后写死为 True，可能出现未校验却显示通过。应改为显式检查并收集检查详情、统一非零退出码。
- 该脚本只核对 `supporting_evidence_ids`，没有验证 `against_evidence_ids`。文档关于两种引用都核验的描述不能由当前脚本独立支持。
- 脚本在中途异常时通常没有最终机器可读失败记录；应在 finally 保存失败阶段、异常类型、检查详情、日志路径及清理结果。末尾总体检查失败前已写文件这一点不足以覆盖前面的启动/调用/引用失败。
- 故障清除发生在正常循环，finally 主要靠结束本地子进程；统一场景管理应显式清除并记录，保留过期/强制清理结果。
- 新运行不要覆盖 `examples/optimized-*` 历史证据，应按 run_id 建独立输出目录；旧样本不应被误标为本次实测。

安全与配置范围：Compose 所有发布端口及本地 launcher 均绑定 127.0.0.1，故当前缺少登录/权限控制应列为本地研究边界。控制 API 使用服务白名单、参数约束；未发现现有危险宿主资源动作。若开放远程或新增压力/停服务动作，鉴权和隔离必须先于启用。`.env` 和数据库目录在 git/docker 忽略规则中，示例模型字段为空；本次未读取或打印真实密钥。local launcher 将完整环境复制给模拟服务，模型密钥可能被不必要地继承；Compose 共享 app 环境也把模型字段给只读采集服务。应按进程最小需要传递。没有自动化秘密扫描测试或依赖漏洞检查证据。
