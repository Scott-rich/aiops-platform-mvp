## 已确认问题与优先级

1. **P1：目标证据可被无关流量完全挤出。** `Store.evidence()` 对所有服务先按时间读取前 20,000 条，再在 Python 筛选服务/trace。临时数据库实际探针中，20,000 条无关事件之后存在目标事件，得到 `range_candidate_count=20001, scanned=20000, related=0, selected=0, truncated=true`。必须改为 SQL 层筛选目标服务、扩展相关 trace，再做稳定分页；提高常量不能修复。
2. **P1：长异常 trace 被模型上下文整包丢弃。** `prompt_records(limit=48)` 为完整 trace 预留健康基线；任何超过预算的异常 trace 均跳过。实际探针：49 条异常 span 同一 trace + 1 条健康 trace，输出只有 healthy，异常计数 0。需要保持异常证据优先、显式记录省略和有界 trace 摘要，不能让输入仅剩健康事件。
3. **P1：候选服务与支持证据混淆。** `heuristic()` 将所有服务最慢的最多 5 条异常 leaf 放入一个候选，以第一条服务命名。实际探针：payment 1000 ms、inventory 900 ms 独立失败，唯一 payment 假设同时引用 inventory-error；应按服务/实例/trace 分组生成多个候选，并标注证据关系。任意其他健康服务的 span 也被当作反证，语义不可靠。
4. **P1：模型输出可指认未观测服务。** 现有校验只核实 event_id，实际接受 `service=service-absent-from-input, confidence=high, verification_steps=[]`，引用一个真实 ID 即可通过。应校验服务/证据关系、明确不确定状态、依据及必需验证步骤；不能把引用存在视为推断正确。
5. **P1：恢复确认未约束故障实例。** incident 使用 root_instance_id 关联，但 `_recovery()` 只按 service 查询健康请求。原故障实例停止上报、同服务其他实例健康时存在误确认风险。此项为静态代码发现，尚未实际复现，必须补多实例测试后修复。
6. **P2：claim 后崩溃永久耗尽诊断资格。** `_claim_model()` 在 HTTP 前写 claimed；无 lease/过期/attempt 状态恢复。需保留调用上限，区分未发送、结果不明和已成功；不能无条件重放请求造成费用重复。当前策略更接近“最多一次尝试”，不保证一次完成。
7. **P2：新证据不一定生成新报告。** `refresh()` 对已丰富版本只检测服务/候选改变或缺失计数下降；同服务新错误码、反证、指标显著改变可能被忽略。模型旧结论亦可能在引用仍存在时复用。应基于语义证据摘要判断变化，并分离实际推理输入 hash 与当前报告上下文 hash。
8. **P2：列表内存开销与恢复证据范围。** `list_versions()` fetchall 全部完整报告再摘要，`list_reports()` 也解析多个大快照；应保存/查询摘要列并分页。`_snapshot()` 结束时间基于异常窗口，未明确涵盖 resolved_at；需测试原始健康恢复证据能否进入最终报告。
9. **P2：坏案例文件阻塞诊断。** `retrieve()` 对每个 JSON 无异常隔离/结构验证；单个损坏文件可使规则报告创建失败，后台持续重试。应记录跳过原因并继续有效案例。

## 实际执行的检查

本次只使用临时数据，不调用外部模型、不操作真实故障或已有数据库。

- 阅读上述源文件、现有相应测试及文档。
- Python 3 个定向静态/内存探针，命令形式为 `python - <<'PY'`，调用 `prompt_records`、`heuristic`、`validate_analysis`：执行成功 3 项，确认上述问题 2–4；输出分别为仅 healthy、跨服务 support 引用、未观测服务 accepted=true。这些是缺陷复现，不能计为产品功能通过。
- 证据子审计员临时 SQLite 探针：纠正两次不符合现有插入格式的探针后成功 1 次，确认问题 1；未修改源码。
- 针对性自动化测试命令：`python -m unittest tests.test_reporting tests.test_core tests.test_engine -v`；实际结果 **19 通过、0 失败，用时 15.135 秒**。该命令的模型测试为 mock，并非真实模型调用。
- 当前所有真实模型相关环境变量未配置；真实模型调用 0 次，真实模型诊断验收 **阻塞**。

## 推荐修改顺序及验收

遵守总任务顺序：先由 Kafka/Flink 负责人打通真实链路，再实施下列模块。保留旧 API、报告 JSON 和规则回退；数据库只做向后兼容的增量 schema，修改前备份，禁止原地覆盖历史报告。

| 次序 | 文件范围 | 具体修改 | 验收 |
| --- | --- | --- | --- |
| LLM 基础 | diagnosis.py、新增配置/模型测试文件、.env.example | HTTP adapter 配置/超时/有限重试/429 限流；结构模型、unknown、服务及引用校验；调用时间/usage/费用来源；预算状态恢复 | 本地 HTTP stub 实测 header/请求、500/429/超时/非法 JSON/错误 refs；规则回退、并发预算和重启测试；独立真实集成命令在无配置时明确 skip |
| RCA | diagnosis.py、incidents.py、retrieval.py、tests | trace 服务依赖图；按服务+实例多个候选及证据；规则/案例/模型来源分别记录后整合；修复实例恢复 | 标记根因数据集覆盖级联、并行两个根因、未知内部原因、健康对照、故障实例失联；量化 Top-1/Top-3；不确定可输出 |
| 证据 | storage.py、reporting.py、api.py、增量迁移、tests | SQL 关联选择、稳定分页和过滤、不可变 evidence_set manifest/统计/hash、完整与截断状态、摘要分页/版本比较 | 1801+、20001+ 数据量，目标服务不丢；跨页无漏/重；冻结集合晚到数据隔离；哈希篡改、筛选边界、恢复证据与旧版本读取 |
| 可维护性 | retrieval.py、engine.py、README/docs | 坏案例隔离、可追踪错误、保留/归档/清理策略和受控命令，成本/阻塞状态文档 | 坏 JSON 不阻塞规则报告；有界查询/重试；归档后报告/证据仍可校验；真实记录执行环境和命令 |

风险：无模型配置无法满足真实调用；新增字段要支持读旧报告；证据 manifest 会增加存储，清理必须识别被历史报告引用的成员；模型重试需同时受单事件预算约束；服务关联来自观测关系，不等同于内部因果。
