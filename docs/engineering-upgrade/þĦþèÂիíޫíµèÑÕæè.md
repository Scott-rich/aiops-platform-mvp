## 关键缺陷及优先级

1. P0：真实 Kafka → Flink → Kafka → worker 链路未经验证。先运行，再修复运行时发现的问题。
2. P0：`flink.rules.validate_metric` 对 `10**1000` 抛 OverflowError；app 接受小数 event_time、未来120s，Flink拒绝；app限制字符串256字符而Flink不限制。统一轻量契约并测试 poison input。
3. P0：相同 event_id 不同检测值导致 accumulator 确定性失败；应用端却静默忽略。统一为可审计的冲突隔离，避免恢复后再次失败。
4. P1：source value-only 丢 Kafka 元数据；source 后生成 watermark 无分区级事件时间隔离。用真实3分区偏斜实验判断并修复，不能假装存在 Python builder API。
5. P1：恢复只是配置。需要完成 checkpoint、停止/恢复真实任务并验证窗口状态/offset；明确重新重放与 checkpoint恢复的区别。
6. P1：LLM prompt 对超过48条的异常 trace 整包跳过，可导致只选健康证据；模型无可配置超时/限流/有限重试/耗时成本、unknown结构状态；崩溃claim无lease恢复。
7. P1：规则单候选可混用多个叶子服务的支持证据；恢复查询按服务未按实例隔离；证据 SQL 先LIMIT后关联筛选可能被忙服务挤掉。
8. P0：旧 `verify_optimized.py` 用 assert 执行验收，`python -O` 可删除关键检查；成功字段部分写死、只核对支持引用而未核对反对引用、早期失败不落结果。验收工具必须先修正，失败运行必须保留。
9. P2：证据分页、完整清单、动态阈值、10类故障、性能/可靠性基准与工程化均需分阶段落地。

## 数据与可靠性边界

SQLite WAL、事件/告警主键和报告不可变机制有效，应保留。进程内快速检测状态重启丢失；producer未成功投递的遥测无持久恢复；Kafka单副本、共享本地checkpoint不构成高可用；全流静默不推动事件时间尾窗口。所有边界必须进入最终验收矩阵。
