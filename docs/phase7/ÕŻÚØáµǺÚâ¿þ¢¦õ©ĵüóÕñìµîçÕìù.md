# 第七阶段：可靠性部署与恢复指南

本阶段在第六阶段上增量修改，不改变事件、告警、报告的既有字段或公开路由。新增三个SQLite表，修复故障链路中的事务、状态与超时问题。结果与原始失败日志见[验收报告](第七阶段验收报告.md)。

## 从干净环境复现

使用Linux/WSL、Python 3.11/3.12；真实Kafka/Flink还需要Java17、首次下载运行时的网络和足够的内存/磁盘。没有新增常规Python依赖，版本继续固定于requirements.txt。Flink使用单独的Python3.11运行时，不向业务虚拟环境安装PyFlink。

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python -m unittest discover -s tests -v

# 只准备Kafka：下载并核验官方校验和。
python -m scripts.bootstrap_fault_kafka --runtime-dir /tmp/aiops-phase7-kafka
# 每次使用不存在的输出目录；脚本启动和清理自己的回环服务。
python -m scripts.verify_reliability \
  --kafka-home /tmp/aiops-phase7-kafka/kafka_2.13-3.9.1 \
  --output artifacts/reliability-run-01

# 完整原生Kafka/Flink、TaskManager重启、窗口状态恢复和真实HTTP级联。
python -m scripts.bootstrap_native --runtime-dir /tmp/aiops-phase7-native
/tmp/aiops-phase7-native/venv/bin/python -m scripts.native_streaming \
  --runtime-dir /tmp/aiops-phase7-native --output artifacts/flink-recovery-run-01

# 包含真实Java桥接构造的可选单元回归；不自动调用外部模型。
AIOPS_SOURCE_BRIDGE_JAR=/tmp/aiops-phase7-native/aiops-kafka-source.jar \
AIOPS_KAFKA_CONNECTOR_JAR=/tmp/aiops-phase7-native/downloads/flink-sql-connector-kafka-3.3.0-1.20.jar \
/tmp/aiops-phase7-native/venv/bin/python -m unittest discover -s tests -v
```

`verify_reliability`和`native_streaming`返回0表示本次检查通过，1表示失败；失败也保存JSON、检查明细和日志。输出目录不覆盖已有数据。`verify_reliability`的输入是明确标记的生成遥测，传输与worker/API/数据库为真实进程；`native_streaming`还运行四个实际HTTP服务。它们不是容量压测，性能与效果评估继续使用第六阶段工具。

Docker/Compose保留原先启动方式，并传入新增配置，但本轮没有Docker运行时，镜像构建及Compose部署仍未实测。原生通过不能替代容器验收。单broker、单SQLite和本地checkpoint均不构成高可用。

## 事务和投递边界

正常路径：Kafka poll → 完整校验 → SQLite事务（事件ID去重、连续错误状态、快速告警、事件关联、打开通知）→ commit数据库 → 提交Kafka offset → 异步报告补充。

- 连续错误状态按`service + instance_id`存于`pipeline_fast_state`。重启后第四个错误不会被遗忘，第五个新错误可触发一次；重复ID不再计数。状态与原始遥测共同提交，事务失败一起回滚。已经触发的标志也持久化，健康观测重置。
- Kafka投递仍为至少一次；事件、告警、事件关联使用已有业务ID幂等。不是Kafka与SQLite之间的分布式事务。若落库后offset提交失败，worker退出，监督进程重启后重放并去重。
- 坏消息独立保存后才能提交offset。若同poll后续事件写入失败，DLQ可能先落库；`deadletter_keys`按Kafka坐标、原文和原因去重，重放不会重复插入同一收据。不同offset是不同收据；旧版已有DLQ不自动回填去重键。同坐标同正文的topic删除重建不在身份保证范围内。
- Fast状态默认最多512个服务实例键，每键保留最多5个错误。超限淘汰最旧状态并记录日志；被淘汰键的部分错误序列会丢失，重新收集后才能触发。原始事件不会删除。
- 报告线程不参与摄取事务。报告版本、证据快照、事件状态、本地通知outbox、模型预算仍持久化于SQLite。通知表仅供本地查询，本轮没有发送外部消息。

## 超时与有限重试

| 环境变量 | 默认值 / 范围 | 行为 |
| --- | --- | --- |
| `DB_TIMEOUT_SECONDS` | 3 / 0.05–30秒 | 每次进程锁获取及SQLite锁等待；两类等待可能累加 |
| `WORKER_STORAGE_ATTEMPTS` | 3 / 1–5 | 可重试存储操作的总尝试次数，含首次；指数退避从0.2秒开始，单次最多2秒 |
| `WORKER_COMMIT_TIMEOUT_MS` | 15000 / 1–60000 | offset提交的总超时，失败退出，不继续poll后面的批次 |
| `WORKER_CONNECT_ATTEMPTS` | 12 / 1–100 | Kafka初始连接的总尝试次数，间隔2秒 |
| `WORKER_POLL_FAILURES` | 5 / 1–100 | 连续poll或空闲broker探测失败上限，退避1/2/4/8/10秒 |
| `FAST_STATE_MAX_KEYS` | 512 / 1–4096 | 持久化连续错误状态键数上限 |

SQLite仅对BUSY/LOCKED/CANTOPEN/IOERR等可重试OperationalError重试；数据损坏和缺表等错误直接失败，不自动修复或删除数据库。HTTP数据库错误返回503；本地HTTP模式现在复用这一处理器。

Kafka空poll每5秒通过`end_offsets`探测已分配分区，无分配时使用既有metrics主题的0号分区；内部总超时由15秒`request_timeout_ms`限制。不要改回`bootstrap_connected()`：它只看引导连接；也不要直接用`topics()`作为有界探测。本轮实测发现固定依赖kafka-python 2.2.12的该元数据路径可能无限等待。offset提交必须显式传`timeout_ms`。核对依据：[该版本API文档](https://kafka-python.readthedocs.io/en/2.2.12/apidoc/KafkaConsumer.html)及已安装依赖源码。

生产运行仍需进程监督：Compose已有`restart: unless-stopped`。本轮原生测试只对测试拥有的worker提供最多两次重启，实测覆盖broker恢复后消费组身份失效导致提交失败的情况。单次操作有限重试不代表监督系统永不重启；持续故障必须排查日志和基础服务。

## 恢复确认规则

availability/latency故障需要10秒窗口至少10个request；CPU/内存需要15秒窗口至少3个host样本。最新数据不早于5秒前，采样起点须覆盖窗口前部，相邻采样间隙最多5秒，窗口不能出现异常。还必须持续满足默认10秒健康保持期。

新增约束：根因实例明确时必须看到该实例的健康数据；只看到其他实例健康不能确认恢复。根因实例未知或规则没有已知健康定义时保持不确定。检查中断超过一个采样窗口、时间回退或旧版保持状态无检查时间时，重新开始保持期。恢复查询最多读取50001行，发现截断时不确认恢复。新异常、缺样本、未来时间样本、缺少根因实例数据均不能当作已恢复。

这验证的是观测健康，不保证业务语义已完全恢复；时间同步、低流量和采样缺失会使确认推迟。

## 旧库升级、备份与回退

首次发现缺少phase7表时，Store持有已有进程访问锁，通过SQLite在线backup API创建`DATA_DIR/backups/before-phase7-<uuid>.sqlite3`；完成并发布备份后才在事务内新增`pipeline_fast_state`、`deadletter_keys`、`platform_migrations`。备份失败即停止迁移，原有表不删除。新建空库无需备份。原有事件ID索引、报告版本和模型预算不变，升级前的内存快速检测状态无法事后恢复。

先在独立输出目录验证你自己的旧库：

```bash
python -m scripts.verify_storage_upgrade \
  --source /absolute/path/to/old-data/aiops.sqlite3 \
  --output artifacts/my-upgrade-check
```

工具对源库做在线备份，只升级副本，逐表流式校验原有行数与内容哈希，验证自动备份以及源文件字节不变。建议测试时停止旧库写入；正在写入会使“源字节不变”检查失败，不能把它算作升级通过。

回退时先停止所有写入者，另行保存当前数据目录和WAL/SHM；从迁移前备份建立一个**新的**DATA_DIR，用原版代码只读核对后再切换启动配置。不要在运行中的数据目录直接覆盖数据库、删除WAL或自动回退。回退备份会缺少备份时刻之后的新数据，必须另行处理。

## 哪些数据能恢复、哪些可能丢失

| 数据/情形 | 当前保证与限制 |
| --- | --- |
| SQLite已提交事件、事件关联、报告、模型预算 | 文件仍在且未损坏时跨进程重启保留；已实测历史报告哈希和进程异常退出边界 |
| SQLite事务中尚未提交的写入 | 进程退出后回滚；Kafka未提交offset的数据可重放 |
| Kafka已确认且尚未过保留期的消息 | 本轮单broker进程重启后保留；不保证磁盘损坏、删除topic、单副本丢失 |
| 采集端尚未确认的遥测 | 仍无磁盘outbox；发送失败可能丢失，也可能结果未知，不能宣称零丢失 |
| Flink窗口、去重和source offset | 本轮TaskManager重启从已完成checkpoint恢复；checkpoint磁盘丢失及整个JobManager故障未覆盖 |
| 本地固定窗口游标 | 仍只在内存，长时间停机期间历史窗口可能未补算；事件仍保留。动态模式沿用第四阶段持久化游标/基线 |
| Fast状态 | 当前上限内跨重启保留；升级前内存状态、容量淘汰状态不能恢复 |
| LLM调用结果未知或超时 | 规则回退，持久化调用预算阻止重启后重复花费；本轮只测受控HTTP超时，不代表真实模型已验收 |
| 历史已损坏SQLite | 保留原始记录；本轮通过没有证明历史损坏根因已解决，禁止自动修库冒充恢复 |
