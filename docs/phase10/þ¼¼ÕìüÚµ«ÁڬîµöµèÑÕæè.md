## 真实闭环与模型质量

- 本轮运行 Kafka 3.9.1、Flink 1.20.3、Kafka connector 3.3.0-1.20、Java17、Python3.11。测试覆盖重复/冲突、畸形消息、乱序/迟到、Python/Flink 对照和 checkpoint 恢复。TaskManager 恢复单次观察 **18.141 秒**，不是恢复 SLO；当时有其他验证/构建工作。
- 当前真实 HTTP 故障报告被送入校验过 SHA-256 的 **Qwen2.5-1.5B-Instruct Q4_K_M**，llama-cpp-python 0.3.19 真实 CPU 推理；1 次 HTTP 模型调用，候选服务 `payment`，结果通过 JSON 和真实证据引用校验，持久预算阻止重启后重复调用。
- 单次诊断 **200.292 秒**，prompt 5,372 tokens、输出 298 tokens。未配置价格，`estimated_cost=null`；本地 CPU 成本没有测算，不写成 $0。
- **质量限制必须保留**：该模型虽正确给出有证据支持的服务候选，却给出了 `high` 置信等级，并提出“内部错误或资源限制”的未证实猜测。它同时注明内部根因未知，但结构/引用校验无法验证全部自然语言推理。模型置信度不是校准概率，本轮未对这一语义缺口做自动纠正；不能把 8/8 通路检查当作模型因果推断正确率。生产使用前必须继续约束和评估。
- 23,005 条关联证据经过 **116 页**完整读取，分析快照仍限制为 1,800 条并明确标记采样。与 20,100 条无关事件一起测试；历史库只在副本升级，源文件哈希不变；归档、清理、恢复均仅在本轮测试专属数据中执行。
- 恢复验证包含 broker 短暂不可用、未确认消息不冒充已送达、积压追赶、offset重放幂等、数据库锁/503、事件状态和历史报告重启读取。单次 broker 恢复观察约 **8.641 秒**，本次无需监督进程重启 worker。不是高可用承诺。
- 十类故障都有实际清理记录。资源压力仅在本测试创建的子进程中，使用现有时长、内存和单核占用上限；没有宿主资源耗尽操作。

## 失败与修复记录

1. `runtime-first.log`：50 项测试中1项错误。HTTP遥测禁用代理后原模拟入口不再被调用；调整测试验证新 opener、无代理和令牌转发后模块回归通过。
2. `runtime-http-01`：13/14检查通过，关闭检查误将 Uvicorn 正常完成清理后重发 SIGTERM 的 -15 当作失败。根据已安装版本源码核对，改为同时检查退出码与平台/服务器关闭完成记录；新增回归，后续14/14通过。
3. `acceptance-01`：365项中1项错误、10跳过。存储启动检查改变了损坏库行为；现在分别验证拒绝启动与运行期503，均保留损坏原文。最终回归通过。
4. `acceptance-final`：运行时记录证据步骤通过，但之后磁盘进度文件回退成 `running`，哈希不匹配；**该轮汇总不作为最终验收依据**。原因无法仅凭现有证据确定，可能涉及运行目录同步；没有伪造或改写为通过。修复为原子进度写入、不可变终态文件、runner结束再校验哈希与拒绝复用旧输出目录。重跑 `acceptance-terminal`，终态及引用文件复核通过。这个修复不构成对底层文件系统/同步服务一致性的保证。

## 未通过的完整验收条件与下一步

- **Docker**：当前环境没有 Docker，不能验证镜像构建、Compose clean deployment、容器内权限和启动顺序。已做的 YAML/loopback/API探针检查仅是静态检查。
- **外部模型**：未提供外部端点/模型/密钥，本轮真实模型为本地 CPU 兼容接口；外部商业API、实际账单没有验证。
- **模型语义质量**：进一步建立有人工根因标签的数据集，评估内部原因猜测和置信度，并在产品中明确呈现不确定性；不能只靠 JSON Schema 宣称消除幻觉。
- **生产运维与HA**：令牌模式不是完整用户系统，仍需TLS、令牌轮换/撤销、限流、身份审计和网络隔离；SQLite/单broker/本地checkpoint没有多副本高可用验证。
- **迁移与安全**：本阶段未建立通用迁移框架，沿用既有加表/备份机制；依赖锁文件没有包哈希、镜像摘要，也没有完成完整漏洞审核。应在目标部署环境备份后验证。
