# 第三阶段验收报告

## 结论

第三阶段RCA功能已实现并完成自动化与真实链路验证；**仍保留存储可靠性阻塞，不宣称整个平台已完成验收**。第二阶段真实大模型诊断未通过，按用户明确指令继续第三阶段，本阶段没有再次调用真实模型。

最终完整回归：210通过、0失败、2跳过，共212项，35.28秒。真实HTTP故障/恢复检查12/12通过；真实Kafka/Flink第二次运行25/25通过，耗时120.497秒，实际TaskManager checkpoint恢复14.851秒。首次分布式运行在16项检查通过后再次发生SQLite索引损坏，后9项未执行；第二次通过不能证明损坏问题已经解决。

## 失败记录、修复与兼容性

最初报告集成54项中53通过、1错误：旧独立服务测试错误复用了另一服务的同trace/span标识，导致新RCA正确判为歧义后旧断言越界。修正独立样本ID并保留模糊span的专用测试，复测通过。独立审查发现损坏RCA结构触发异常、空trace关系被接受、topology忽略完整性结果；已修复为明确false/409，加入自动化测试。残差字段父/子事件ID也逐一验证存在，未宣称证明精确自耗时或重算全部残差因果。

本轮首次native中的数据库293页，却有索引引用295、304、306页，worker在恢复查询时停止。原始损坏库SHA-256：10c4f0416e93ade28fd6c2605b08530878ecf043e2c1058ca65b1f2200d43a4d；只读检查前后不变。取证在native-attempt-01/readonly-storage-forensics.json。没有REINDEX、修复或覆盖原库，没有确认是SQLite本身、并发、文件系统或checkpoint造成。既有串行锁后仍出现，不能称风险消除。

新临时库2000条顺序写读未复现。第二次native退出后完整性为ok（434条事件、5个事件记录、10份报告）；HTTP运行在线backup归档完整性ok（3994条事件、1事件、3版报告），见post-run-storage-integrity.json。它们是本次成功样本，不能代替损坏触发条件调查。失败批次不提交Kafka offset，但未证明损坏库中所有既有已提交事件均可恢复。

旧报告不补造RCA，旧接口仍可读取。新版本冻结snapshot/RCA哈希和证据集。篡改检测校验引用存在及父子关系，SHA是内容一致性而非外部签名。控制台将不可信内容作为文本，证据按钮固定绑定对应报告快照；30节点/60边显示上限会提示，当前快照内完整JSON保留。

## 未解决、依赖与下一步

1. **存储可靠性：本阶段再次观察到SQLite损坏，原因未确认，阻止生产可靠性验收。** 下一步先做最小并发/文件系统/连接生命周期复现和Kafka已提交offset对账；测试等待报告时还应尽早报告worker失败，避免50秒空等。
2. **第二阶段：真实模型仍未验收。** 最后历史真实CPU调用324.347秒、输出截断、规则回退；本阶段没有重试。有效云模型配置需用户自己的环境变量，密钥未硬编码；RCA规则链路不依赖API密钥/GPU。
