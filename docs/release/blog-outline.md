# 从“链路能跑”到“结论能复核”：AIOps 研究改造手记

**用途：可扩写成中文技术博客的详细大纲。** 以下按论证顺序组织正文、图和可核验材料；不把未完成的集群验收写成成功经验。数值以链接的结果文件为准，原始失败保留。建议标题直接点出证据和评估，不使用“领先”“提升数倍”等没有对照支持的词。

## 开场：运行演示为什么不能直接变成论文结论

先描述一个读者容易理解的现场：服务请求开始变慢，监控出现告警，系统展示一份措辞完整的根因报告。演示顺利结束，只能说明组件在这一输入下完成协作，不能说明报告中的服务真是故障源，更不能说明换一套系统仍然有效。日志、指标和链路都是观测；它们可以支持候选解释，却不自动赋予解释因果地位。文章的中心问题由此展开：怎样让每一个“检测到了”“定位正确”“防御有效”都有清楚的分母、对照和失败路径。

交代项目原本已经具备 Kafka、Flink、SQLite、报告版本与本地模型接入。这些工程资产应保留，不需要为了研究重写所有功能。真正的变化是建立证据边界：公共匿名 KPI 用于离线检测方法比较；合成场景用于验证 RCA 协议；原生服务验收证明进程与消息链路；真实业务集群实验必须另有部署和注入证据。读者应先看到这些区别，才不会将一种成功误读成另一种成功。

## 第一部分：把数据来源、训练过程和测试过程分开

解释如何把 SMD 与 PSM 封装成统一接口：训练矩阵、训练标签假设、测试矩阵、测试标签和元数据分别返回，元数据包含实体名称、维度、缺失值处理和原始文件哈希。下载器固定官方仓库提交，下载完成才写清单，数据不混入代码仓库。这样读者得到的不是“某个同名数据集”，而是可以逐字节检查的输入。公共数据本身不包含这套微服务的服务名，不能随意把匿名维度改叫 payment 延迟。

重点展开两个容易忽视的泄漏点。第一，缺失值填补只能从训练列学习；如果用全量数据的中位数，会悄悄把测试分布带回训练。第二，PSM 的时间戳不是业务特征，直接当数值维度可能得到依赖时间趋势的分数。这里的验证不是看结果是否漂亮，而是构造训练与测试差异很大的小例子，检查变换只由训练数据决定。对无法可靠确认的采样间隔，明确保留空值，不猜测秒或分钟。

SMD 采用事先声明的字典序机器子集，不能跑完再挑表现好的机器。各机器单独拟合，各方法用同样输入与随机种子列表。训练假设、实体数量和逐行结果都能从[主实验](../../research/results/p0-smd-03/result.json)追溯。PSM 是单个归池实体，不能把多个 seed 说成多个独立生产环境；这个区别影响后续所有置信区间的解释。

## 第二部分：四种检测器比较的到底是什么

先用直观语言介绍固定标准差阈值、中位绝对偏差、Isolation Forest 和流式 POT。前三者提供不同的异常得分或决策方式；本项目 POT 在 ZScore 得分上更新尾部阈值，因此两者的排序指标相同是设计结果，不是数据抄错。POT 的实现是周期性最大似然重拟合的工程变体，并非原论文求解器的逐位复现。文章应把算法名称、实际实现与论文之间的距离讲清楚。

随后解释阈值和排序指标的区别。PR-AUC 看得分排序，固定阈值下的 precision、recall、F1 看具体决策；两个方法可能排序相同，却产生不同的告警数量。线上运维还关心一次真实异常被切成多少段告警，所以需要报告连续预测阳性区间与真实异常区间的比例。若只挑一个最好的指标，读者无法判断一个方法是否以增加告警负担换来更高召回。

**图一配文建议：** 曲线来自同一冻结实验的真实得分文件。先讲坐标轴和类别不平衡，再说明机器差异为什么不能被单个平均值抹平。链接到[逐实体结果、全部指标和不确定性](../../research/results/p0-smd-03/result.json)，不要仅放一张没有来源的高分图片。

## 第三部分：一个看上去很高的 PA-F1 为什么可能误导

用本次 PSM 的 POT 结果举例：逐点 F1 是[0.0123](../../research/results/p0-psm-03/result.json)，point-adjust 后成为[0.8496](../../research/results/p0-psm-03/result.json)。这不是可以直接宣传的能力提升，而是评价规则把同一个真实异常区间内的零星命中扩展成整段命中。写作时先说明转换规则，再展示同一预测对应的两个分数，让读者理解为什么“评价器”会改变故事。

本文同时保留未调整的逐点指标、PA、覆盖比例达到预设要求才扩展的 PA%K、范围召回与告警负担。没有哪一种指标可以独自承担所有结论：逐点指标对边界敏感，事件指标可能容忍较长延迟，PA 容易奖励稀疏命中。更可靠的表达是明确运维目标，再用多个互补指标共同约束解释。

统计段落使用 SMD 的 MAD 与 ZScore 对比。平均 AP 差和实体 bootstrap 区间可在[结果](../../research/results/p0-smd-03/result.json)中找到，但配对 Wilcoxon 的[p=0.125](../../research/results/p0-smd-03/result.json)不足以支持“显著优于”。PSM 上排序还出现反向变化，因此结论只能是该子集上的观测差异。小样本、有依赖的实体、探索性多重比较都应作为解释的一部分，而不是文章末尾一行格式化免责声明。

## 第四部分：让 LLM 的失败也成为正式结果

从证据键协议入手：模型只能选择输入中的引用键，系统再把键映射回事件与服务，保存原文哈希、归一化结果和校验状态。这个设计可减少凭空引用，却不能保证被引用事件足以证明根因。合法引用、正确证据选择和正确诊断是三个不同问题；它们需要三个不同的检查，不能用“schema 通过率很高”替代诊断准确率。

介绍合成金标准的生成与分层切分。场景覆盖正常、延迟、错误、依赖、资源和噪声；标签来自构造规则，人工复核尚未完成。dev 用于提示和校准，test 冻结后只按声明的实验臂执行。文章可以展示 frozen-before-test、排他运行锁和原始 JSONL 的作用：读者能够核对先冻结后测试的时间顺序，而不是只能相信作者一句“没有泄漏”。

本次小模型的负结果必须放在正文：大量弃权、故障证据召回低、强制选择仍存在较多错误。准确率需要区分正常时正确弃权与故障时正确定位。若模型没有生成任何引用，引用级未知键率的分母为空，应显示 null，不能写成零幻觉。这样的结果可能不利于宣传，却清楚指出下一步该改善任务表达、数据标注还是模型能力。

**图二配文建议：** 先读样本量、重采样单位与区间，再读柱高。具体文件名以[图表结果目录](../../research/results/p1-comparison-01/result.json)为准。链接[模型主表](../../research/llm/RESULTS.md)，同时展示原始与校验后分数，不把被安全层拒绝的输出当作成功交付。

## 第五部分：弃权是一个可选择的动作，不是免于评估的理由

解释风险—覆盖曲线：系统少接单可能降低接受集合的错误率，但当所有案例都不接受时，覆盖率为零，风险没有定义。图上应明确标出未定义点，而不是画出一个看似完美的零错误点。开发集上冻结阈值后，测试阶段只评估该规则；不能看到测试成绩不好，再改阈值并继续称它是保留测试。

介绍 token 似然代理与正确概率的区别。模型擅长生成流畅句子，不代表句子中的服务判断正确；需要用开发集校准，并在测试集报告 ECE。即便 ECE 有数值，样本依赖、家族过少和同分置信度都会影响解释。强制服务选择是预先声明的独立条件，必须真实调用模型，不能把规则 RCA 排名补进来冒充不弃权基线。

## 第六部分：审计发现评分错误时怎样修正

这一节可以作为全文最有价值的工程细节。攻击集不仅包含不存在的键和显式越权指令，也包含格式完全合法、但引向错误证据的目标。原计分器漏掉后一类，独立审计用原始输出复算后发现差异。正确处理是保留原始结果，用一个只读修正脚本生成新结果，并标注事后修正；不是覆盖旧 JSON，更不是重新跑模型直到得到想要的数字。

防御前后比较还要报告效用。攻击率下降可能伴随证据召回下降或所有输出被拒绝，因此同时报告原始召回、校验后召回、clean 正确性和冻结覆盖率。若 clean 本来就不正确，就没有可用于估计“正确诊断被破坏”的有效样本。攻击类别共享基础案例，不能把所有变体当成互相独立的世界。链接[修正结果](../../research/results/p1-05b-correction-02/result.json)，让读者可以检查具体命中与配对差值。

## 第七部分：工程化不是只加一个 CI 文件

列举本轮实际改动：固定依赖、自监控指标、版本化 API、认证前置、规范路由限流、单副本 SQLite 部署约束和失败保留。CI 文件只有被真实执行且门禁不能被忽略，才形成远端绿色状态；本轮只能证明本地工具链与隔离红→绿探针有效，不能贴一个虚构的远端成功徽章。覆盖率也应报告范围与排除项，不能通过排除难测逻辑或批量 pragma 把数字抬高。

进一步讨论审计暴露的边界。真实服务器默认代理头处理可能使应用层所谓“直连 IP”其实来自转发头；修正启动参数并用真实 HTTP 请求验证，才能完成承诺。深嵌套 JSON 会触发递归错误，消费者必须先确认死信写入，再提交位点，避免毒消息反复重启。故障注入创建成功后即使日志写盘失败，清理仍必须运行；创建冲突则不能删除别人的对象。这些细节比增加一个展示按钮更直接决定实验可信度。

## 第八部分：分布式的证据范围应该怎样写

展示原生 Kafka/Flink 验收记录，说明实际启动了什么、验证了哪些消息与恢复路径。短时性能检查用于发现明显回归，不等于长时容量测试；HTTP 请求率不等于遥测事件率；一个进程的 RSS 不等于整个平台占用。不同结果使用不同冻结源码，必须给出版本映射，不能拿旧测试替新代码背书。

![图三：PSM 跨方法 PR 曲线](../../research/results/p0-psm-03/pr-curves.png)

**图三配文建议：** 用另一公共数据集说明结果不普遍成立，并把读者带回外部效度问题。不要为了凑“分布式性能图”画出尚未采集的吞吐曲线。真实集群实验的空值比一张漂亮的假图更有信息。

介绍已准备的 Online Boutique、Collector、Chaos Mesh 和评估器，同时明确当前没有可用的 Docker/kind 环境。计划中的故障不是已执行故障，生成的 YAML 不是部署成功证据。三节点 kind 仍是同一物理机上的容器；需要控制器确认、原始 ground truth、同批 Prometheus 对照、删失统计和资源记录，才有资格讨论故障检测或恢复分布。

## 结尾：可交付代码与通过全部研究门禁是两件事

最后回到文章开头的报告：它现在不只是一个可读页面，还可以追溯输入、运行版本、原始输出、评分规则和失败记录。公共检测对照已经能复算，本地链路确实运行，小模型不足也被量化。仍然没有取得的人工复核、真实集群和长时负载证据保持未通过，不因交付压力改写状态。

未来工作按证据缺口排序：先完成标注复核与真实 RCA 数据适配，再按部署说明开展真实故障与资源采集，最后才考虑更大模型和自动恢复策略。每一步都应预先声明对照与停止规则。文章最值得传达的能力，是发现结论不成立时仍能保存证据、修正方法、让别人复核，而不是把每张结果表都写成成功故事。


## 附记：怎样让复现者少走一次弯路

发布之前先以陌生读者的顺序走一遍材料：从解压目录找到 README，再运行最短演示，检查输出目录是否真的生成结果文件，随后沿链接找到完整实验命令。文档中的绝对临时路径记录原始执行位置，复现命令则应提供可替换的新路径；二者不能混用。模型和原始公共数据体积大，交付包保留下载来源与哈希，同时保留原始推理输出和得分矩阵，使读者无需先下载权重就能核对评分。

失败记录也需要索引。测试失败、日志不完整、过期评分和未执行门禁分别是什么原因，应在同一验收对照中标清楚。旧结果的存在不说明当前版本仍有同一错误，但当前修复也不能倒过来改写旧结果。更新后的门禁需要自己的命令和时间戳，评审者才能判断修复是在看到问题之后发生，而不是临时替换了一个更有利的输出文件。

哈希本身不能证明实验科学合理，它只能帮助检查“现在看到的字节是不是当时的字节”。因此完整交付同时需要实验设计、原始数据边界、独立审计和失败解释。源码提交历史也不应伪装成长期积累：本次实际形成的模块化提交使用真实时间，不重写成过去数月的开发经历。仓库变小是因为大产物外置并有可追溯位置，不是删除不利证据。

读者复现时还应区分运行失败与研究结果不好。前者可能是依赖、版本或环境的问题，需要修复后用新目录重跑；后者可能说明假设不成立，应保留为结论。一个可靠研究平台的价值，是让这两类问题都可以被定位，并使下一位使用者知道自己需要准备什么、能够验证什么，以及哪些判断现在仍然没有答案。
