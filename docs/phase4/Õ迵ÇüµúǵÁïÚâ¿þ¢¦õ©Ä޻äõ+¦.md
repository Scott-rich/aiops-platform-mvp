# 第四阶段：动态检测部署与评估

## 开启与兼容性

默认 `DETECTION_MODE=fixed` 保留原有 Python 精确 P95、Flink 25ms直方图、800ms/20%/90%固定阈值，以及各自告警ID。独立的连续5次5xx快速预警在两种模式均保留。动态参数只影响动态模式。

在项目根目录运行（Python3.11/3.12）：

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
# 首次可复制示例；已有.env应先自行备份，仅修改检测相关键。
cp .env.example .env
# 将.env中的 DETECTION_MODE=fixed 改为 dynamic
python -m scripts.local_platform --data-dir data-phase4
```

或者直接运行 `DETECTION_MODE=dynamic python -m scripts.local_platform --data-dir data-phase4`。环境变量优先于`.env`。本地启动器只读取明确白名单键，不执行shell配置。无需模型API密钥，示例未包含真实密钥。

Compose使用相同`.env`检测变量，传给Flink三个服务和提交容器：

```bash
docker compose config
docker compose up -d --build
```

**已有Flink作业不会因修改`.env`自动切换模式。** 必须先保全checkpoint/savepoint和数据库，明确停止旧作业，重建相关容器并提交新作业。固定模式保留 `window-rules-v3` UID；动态模式使用 `adaptive-window-v1` 和 `adaptive-baseline-v1` 全局keyed state。禁止将固定模式checkpoint直接用于动态模式，也禁止使用 `--allowNonRestoredState` 掩盖状态丢失。动态配置改变后指纹不一致会失败关闭；需备份后从Kafka历史重放暖机，不能声称无缝迁移。两个模式不可同时写同一告警/事件数据库做效果比较，应使用评估脚本或隔离的数据目录与主题。

本轮Docker/Compose只做静态解析，实际容器部署未验收。原生Kafka/Flink实测与容器验收分别记录。

## 算法、参数与限制

每个服务、指标、UTC时段独立维护历史。四个指标为P95延迟、5xx比例、平均CPU和平均内存。只处理严格递增的已关闭窗口；当前窗口从不参与当前阈值拟合。基线采样间隔至少为窗口长度，避免把30秒/10秒滑窗当成三个独立历史样本。仅正常或暖机窗口进入历史，检测到的异常不学习。

阈值为以下三项的最大值：

- 历史中位数 + `sigma × 1.4826 × MAD`；MAD是历史值与中位数之差的绝对值的中位数。
- 历史中位数 × `(1 + relative_margin)`。
- 历史中位数 + 指标绝对容差。

P95阈值向上取整至25ms桶边界，使用与Flink一致的直方图特征；60秒溢出桶在动态延迟通道中明确弃判，不能冒充25ms精度。其他指标可继续检测。严格 `值 > 阈值` 报警。

| 配置 | 默认 | 含义 |
| --- | ---: | --- |
| DETECTION_MODE | fixed | fixed或dynamic |
| DETECTION_MIN_REQUESTS / MIN_HOSTS | 20 / 3 | 当前窗口请求/主机样本下限 |
| DETECTION_MIN_WINDOWS | 12 | 每个时段/指标至少12个历史窗口后才判断 |
| DETECTION_HISTORY_WINDOWS | 120 | 每组最多保留120个值 |
| DETECTION_BUCKET_HOURS | 6 | UTC分桶宽度，必须整除24；每桶单独暖机 |
| DETECTION_MAX_AGE_MS | 604800000 | 7天事件时间历史有效期；Flink另有相同长度处理时间state TTL |
| DETECTION_SIGMA | 3.0 | MAD倍率 |
| DETECTION_RELATIVE_MARGIN | 0.2 | 相对容差 |
| DETECTION_LATENCY_MARGIN_MS | 50.0 | 延迟绝对容差 |
| DETECTION_ERROR_MARGIN | 0.05 | 错误比例绝对容差，即5个百分点 |
| DETECTION_CPU_MARGIN / MEMORY_MARGIN | 5.0 / 5.0 | 资源指标绝对百分点容差 |
| DETECTION_MAX_SERVICES | 256 | 本地持久化服务上限，超限按最旧窗口淘汰并记录warning |

参数在启动时进行类型、有限值及范围校验。完整名称见`.env.example`。默认30秒窗口下，12个非重叠基线窗口约需6分钟健康流量，外加窗口水位线等待；不足时不强判异常。时段变更、基线过期、冷启动和指标缺失会再次进入弃判/暖机，已在评估中计入覆盖率和漏报。

这是一种可解释的简单在线基线，不是经过生产校准的模型。冷启动持续故障可能被学成基线；长期阶跃或渐变不能保证自动适应；主机资源接近100%时较高正常基线可能使阈值超过物理上限。这些情况需要人工确认、调参或在备份后重新暖机。固定模式与快速5xx仍可独立使用。没有日历节假日或自动季节学习。

## 状态与诊断联动

本地动态状态保存在数据目录 `detection-state-v1.json`，含配置指纹、每组历史、持久游标及待发送告警。保存使用SHA-256校验、同目录临时文件、fsync和原子替换，并使用独立filelock。先保存待发送告警再投递，失败后重放同一稳定ID；告警和事件表仍使用原有幂等逻辑。文件最大64MiB，每tick最多补算100个窗口；数据库无结构迁移。校验和不是防恶意篡改的数字签名。

配置变更或文件损坏时拒绝自动覆盖。先停止进程、保全数据目录，将sidecar复制备份后移走，再启动重新暖机；历史告警和报告仍保留。固定模式不读取sidecar。不要删除SQLite文件“修复”状态，也不要同时在多个主机通过共享文件系统写同一个数据目录。

Flink使用服务keyed global state，包含基线和最后窗口结束时间，随checkpoint恢复；历史由事件时间过期和有界队列限制，空闲key再由处理时间TTL过期。服务key总数仍随活跃服务数增长，不能声称全局常量内存。Kafka sink仍是至少一次，稳定alert_id负责业务去重。

动态告警保留原rule_id和schema_version，并附上阈值、基线中位数/MAD、基线数量/首末时间、UTC桶及配置指纹。恢复检查对相应服务使用已冻结的动态延迟/CPU/内存阈值，继续要求新鲜样本、覆盖跨度和健康保持时间；错误率恢复仍要求无5xx，较检测阈值更保守。

RCA新版本 `evidence-graph-v1.1` 只把动态阈值用于告警服务及其窗口中真实存在的证据，不把该阈值套到其他服务。缺少其他服务基线时，传播判断可能不完整并明确提示。旧报告不重写。LLM及历史案例逻辑保持原有机制，真实模型未验收问题未因此消失。

## 复现测试

```bash
python -m unittest discover -s tests -v
python -m unittest discover -s tests -p 'test_adaptive*.py' -v
python -m scripts.evaluate_detection --output artifacts/my-detection-evaluation
python -m scripts.evaluate_detection --input artifacts/my-detection-evaluation/dataset.jsonl --output artifacts/my-detection-repeat
```

评估输出目录须不存在。脚本保存带标签数据、逐窗口逐指标决策`decisions.csv`、汇总`metrics.csv`和`result.json`，含数据哈希、配置、环境和耗时。用户数据采用同样JSONL窗口格式：service/start/end/events/labels；labels为四个指标到bool/null的映射。标签只传给计分代码，不进入检测器；输入须每服务按窗口结束时间递增。自带数据为明确标记的合成故障，不能代表生产准确率。

准确率/精确率/召回率/FPR/FNR以“窗口×服务×指标”为单位；null标签不计分。暖机、低流量等弃判按“未报警”进入全标签混淆矩阵，同时独立报告决策覆盖率，不能靠隐藏弃判提高准确率。故障episode按连续有标签异常窗口定义，漏检episode单列，不把未检测的延迟记为0。检测延迟为**异常起始事件时间到首次报警窗口结束时间**，不是实际Kafka/Flink端到端时延。计算耗时是离线实测函数耗时，不是吞吐量或生产SLA。

真实Flink嵌入式执行（无Kafka）与真实原生Kafka/Flink恢复测试：

```bash
python -m scripts.bootstrap_native --runtime-dir /tmp/aiops-native-runtime
/tmp/aiops-native-runtime/venv/bin/python -m scripts.verify_adaptive_flink_local --output artifacts/my-embedded-test
/tmp/aiops-native-runtime/venv/bin/python -m scripts.verify_adaptive_streaming --runtime-dir /tmp/aiops-native-runtime --output artifacts/my-adaptive-stream-test
```

原生测试只对本次隔离端口、临时Kafka目录和Flink进程操作，正常/失败均执行清理；不接触用户现有服务或调用LLM。测试为加速使用3个基线窗口、24小时桶，并在结果记录配置，不冒充默认6分钟暖机测试。输入为真实Kafka传输的合成遥测。验证重复、乱序、异常输入、迟到DLQ和训练后TaskManager重启，再与相同Python算法逐告警ID及证据比较。

架构参考：Apache Flink 1.20 [窗口和全局keyed state官方说明](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/dev/datastream/operators/windows/)。本项目没有端到端exactly-once、生产高可用或模型正确性保证。
